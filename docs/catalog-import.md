# Загрузка каталога из Excel

Каталог (магазины, товары, цены) готовит команда данных. Backend принимает Excel-файл `.xlsx`
с тремя листами и публикует его в базу одной транзакцией.

**Шаблон для команды:** [`catalog_template.xlsx`](catalog_template.xlsx). В нём лист «Инструкция»
с описанием всех колонок и по одной строке-примеру на каждом листе. Обновить: `make template`.

Схема таблиц команды данных (`дб схема.mmd`) и наша совпадают по каталогу: `products`, `stores`, `offers`.
Таблицы `carts`, `cart_items`, `plans`, `plan_items` в backend тоже есть, но их заполняет приложение,
а не импорт. Чем они отличаются от схемы команды, написано в `docs/decisions.md` (решения 8 и 9).

## Как загрузить

```bash
uv run vezzi import-catalog catalog.xlsx --show-errors
uv run vezzi import-catalog catalog.xlsx --synthetic   # данные демонстрационные
```

Или через API под администратором: `POST /api/v1/admin/catalog/imports` (поле `file`, в Swagger есть кнопка загрузки;
поле `is_synthetic` помечает данные как демонстрационные).

В конце отчёта есть строка «участвуют в расчёте сейчас: N цен». Если N намного меньше общего числа,
цены в файле старые (см. «Свежесть цен»). То же число отдаёт `GET /api/v1/catalog` в `fresh_offers_count`.

Что происходит:

1. Файл читается и проверяется построчно. Плохие строки отклоняются **с причиной** и номером строки,
   хорошие загружаются (D02).
2. Магазины и товары обновляются по своим идентификаторам из таблицы (`store_id`, `product_id`).
   Повторная загрузка не создаёт дубликатов.
3. Цены записываются в новый снимок каталога, и он одной транзакцией становится активным.
   Если что-то пошло не так, активным остаётся прошлый снимок (N04).
4. Повторная загрузка того же файла ничего не меняет (`status: unchanged`).

## Формат

Лишние листы и колонки игнорируются, поэтому в файле могут оставаться служебные данные команды.

**Лист `stores`**

| Колонка | Обязательна | Пример |
|---|---|---|
| `store_id` | да | `1` |
| `chain_name` | да | `Пятёрочка` |
| `store_name` | да | `Пятёрочка, Малый пр. В.О., 52` |
| `address` | да | `Санкт-Петербург, Малый пр. В.О., 52` |
| `latitude`, `longitude` | да | `59.9417`, `30.2654` |
| `store_format` | нет | `convenience`, `supermarket` (по умолчанию) или `hypermarket` |
| `is_active` | нет | по умолчанию `да` |

**Лист `products`**

| Колонка | Обязательна | Пример |
|---|---|---|
| `product_id` | да | `1` |
| `product_name` | да | `Простоквашино Молоко 2,5%, 930 мл` |
| `brand`, `product_type` | нет | `Простоквашино`, `Молоко` |
| `category` | да | `Молочные продукты` |
| `quantity` | да | `0.93` (запятая тоже подходит), можно дробное: `41,5` |
| `unit` | да | `г`, `кг`, `мл`, `л`, `шт` или `м` |
| `attributes_json` | нет | `{"fat_percent": 2.5, "sold_by": "штучный"}` |

Фасовка переводится в граммы, миллилитры, штуки или метры: `0.93 л` превращается в 930 мл,
`41,5 г` остаётся 41,5 г. Текст `—` или `-` в ячейке считается пустым значением (например, нет бренда).
Товары с `"sold_by": "весовой"` в характеристиках **не загружаются** вместе с их ценами: в MVP сравниваются
только целые упаковки (решение капитана, `docs/decisions.md`). В отчёте они идут отдельной строкой, не как ошибки.

**Лист `offers`** (цены)

| Колонка | Обязательна | Правило |
|---|---|---|
| `product_id`, `store_id` | да | Должны быть на листах `products` и `stores` |
| `price` | да | Обычная цена: рубли за упаковку, не больше двух знаков после запятой, больше нуля |
| `card_price` | нет | Цена по карте лояльности. Показывается отдельно, в итог не входит |
| `updated_at` | да | Когда **источник** обновил цену. Без часового пояса считается московским временем |
| `in_stock` | нет | `да`/`нет`/`true`/`false`; пусто = наличие неизвестно, такая цена в расчёт не идёт |
| `match_status` | нет | Если колонка есть, загружаются только строки `matched` |
| `price_type`, `source_product_id` | нет | Справочно (`promo` можно показать как акцию). Значение `card` отклоняется: цена по карте идёт в `card_price` |
| `price_conditions` | нет | Условия акции, до 300 символов |
| `source_url` | нет | Ссылка на товар у источника, только `http://` или `https://` |
| `currency` | нет | Только `RUB` |
| `data_origin` | нет | `synthetic` помечает весь каталог как демонстрационный |

Одна цена на пару «магазин, товар». Время в будущем (больше чем на 5 минут) отклоняется.

## Свежесть цен

В расчёт идут только цены не старше `OFFER_MAX_AGE_HOURS` часов (по умолчанию 24, см. `docs/decisions.md`).
Важно: учитывается время обновления **у источника**, а не время загрузки. Если загрузить вчерашний
файл заново, цены свежее не станут.

Для синтетических данных есть флаг `--shift-timestamps`: время всех цен сдвигается так, чтобы самая свежая
была обновлена «сейчас». Для настоящих цен этот флаг использовать нельзя.

## Разбор таблицы команды от 01.11.2026

Файл `Умная_корзина.xlsx` загружается без ошибок: **20 магазинов, 860 товаров, 6711 цен, 0 отклонённых строк**.
Ещё 140 весовых товаров и их 1157 цен пропущены, в MVP их нет.
Данные стали намного лучше черновика: все строки сопоставлены (`matched`), нет пустых цен, дублей и битых
ссылок, а магазины стоят на одном Комендантском проспекте в пределах примерно 1,5 км. Сквозной сценарий
с OSRM проходит: план из трёх магазинов на 6 товаров считается за 89 мс.

Что стоит передать команде данных:

1. **Цены растянуты на 10 дней** (`updated_at` с 20 по 30 октября). При ежедневном сборе все цены должны
   быть не старше суток. По правилу 24 часов в расчёт попадает только 639 цен из 6711 (даже после
   `--shift-timestamps`). Для локального демо можно временно задать `OFFER_MAX_AGE_HOURS=264`.
2. **Данные сгенерированы, но помечены как настоящие.** Есть `generator_version` и
   `base_price_for_generation`, а `data_origin = store_price_feed`. При этом названия сетей настоящие
   (Магнит, Пятёрочка). Нужно `data_origin = synthetic`, иначе приложение покажет выдуманные цены
   как цены реальных магазинов. До исправления загружаем с флагом `--synthetic`.
3. **Весовые товары**: 140 штук с `"sold_by": "весовой"` и ценой за 1 кг. В MVP их исключили
   (решение капитана), импорт их пропускает. Можно не тратить на них время до конца MVP.
4. **`product_type` с хвостом «(доп.)»** у 28 видов: «Йогурт (доп.)» рядом с «Йогурт». Похоже на след
   генератора. Для поиска аналогов (F10) вид товара должен быть единым.
5. **Нет `store_format`**, а `store_type` у всех `physical`. Формат влияет на время покупок: Bolender
   или «Рыбка & Икорка» явно не гипермаркеты, а METRO наоборот.
6. **Нет цен по карте и условий акций.** SCRUM-47 и SCRUM-52 их ждут: добавьте колонки `card_price`
   и `price_conditions`, импорт уже умеет их читать.
7. **`source_id` повторяет `store_id`**, а ссылки `source_url` похожи на выдуманные
   (`spb.vkusvill.ru/goods/vv100001`). Показывать их пользователю пока нельзя.
8. **Листы `carts`, `cart_items`, `plans`, `plan_items` содержат тестовые данные с ошибками**: в 14 планах
   из 20 сумма не совпадает с позициями, есть планы на 11 ноября (в будущем), позиции планов не из своей
   корзины. Импорт их не читает: эти данные создаёт приложение.

## Разбор черновой таблицы команды (30.10.2026)

Файл `Умная корзина.xlsx` загружается без переделки формата: 5 магазинов, 1000 товаров, 3494 цены
приняты, 379 строк отклонены. Что стоит передать команде данных:

1. **Цены устарели.** Все `updated_at` за 24–25 октября. По правилу 24 часов в расчёт не попадает
   ни одна цена. Для демонстрации можно загрузить с `--shift-timestamps`, но для пилота нужен свежий срез.
2. **Магазины в разных концах города.** Руставели (север), Малый пр. В.О. (запад) и три магазина на
   востоке. Пешком между ними 2,5–3 часа, планы из нескольких магазинов не уложатся в лимит 180 минут.
   ТЗ требует «один выбранный район»: нужно 5+ магазинов минимум двух сетей в пешей доступности друг от друга.
3. **Строки без цены**: 90 строк с пустой `price`.
4. **Несопоставленные товары**: 85 строк `unmatched` (без `product_id`) и 210 `needs_review`.
   Они не загружаются, пока ML не подтвердит совпадение (D03).
5. **Подозрительные цены.** Например, молоко 250 мл за 1047,55 ₽, а 330 мл за 164,10 ₽; разброс цены
   одного товара между магазинами доходит до двух раз. Похоже на генератор, для демонстрации это сбивает
   с толку.
6. **Странные фасовки**: молоко 0,2 / 0,25 / 0,33 / 0,45 / 0,95 л, хлеб «Дарницкий» 40 г. Колонка
   `pack_size_requires_verification` в самой таблице это признаёт.
7. **Нет единиц «шт»**: яйца и подобные товары в штуках пока не встречаются, формат их поддерживает.
8. **Листы `carts`, `cart_items`, `plans`, `plan_items` не нужны**: корзины создают пользователи
   в приложении, а планы считает backend. Эти листы при загрузке игнорируются.
9. **Нет `store_format`.** Не обязательно, но с ним точнее время покупок: в гипермаркете товары
   ищут дольше (см. `docs/planning.md`).
